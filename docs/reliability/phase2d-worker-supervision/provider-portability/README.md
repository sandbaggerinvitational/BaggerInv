## Evidence classes

- **PROVIDER-DOCUMENTED:** Supabase supports pg_cron/pg_net scheduled HTTP with Vault-held credentials. Its Vault guide says SELECT on the decrypted view grants plaintext access and describes encryption that survives logical backups with the encryption key outside the database. Neither guide promises that managed `postgres` can normalize all extension grants. [Scheduled functions](https://supabase.com/docs/guides/functions/schedule-functions), [Vault](https://supabase.com/docs/guides/database/vault).
- **PROVIDER SOURCE:** Upstream pg_net SQL grants PUBLIC schema usage, table and sequence privileges; HTTP functions take URL, body and headers. The queue contains those fields. Supabase's own Vault grant tests include `service_role` SELECT on decrypted secrets and execute on secret-management/decryption helpers. Upstream source is corroborating evidence, not a claim that master equals the hosted extension artifact. [pg_net SQL](https://raw.githubusercontent.com/supabase/pg_net/master/sql/pg_net.sql), [provider Vault privilege tests](https://raw.githubusercontent.com/supabase/postgres/develop/nix/tests/expected/vault.out).
- **OBSERVED HOSTED:** The retained rollback-only probe saw pg_net 0.20.4 objects owned by `supabase_admin`, PUBLIC queue/response/sequence grants and helper execution. The managed installer could not normalize those grants. This task did not reinstall extensions, even in a rolled-back transaction. New read-only checks confirm Vault 0.3.1, its `service_role` schema usage/decrypted SELECT, `postgres` SELECT with grant option, no secrets, and the existing supervisor OFF/unconfigured. [Retained metadata](evidence/RETAINED-PROVIDER-ROLLBACK-PROBE.json), [read-only checkpoint](evidence/HOSTED-CHECKPOINT.json).
- **REPOSITORY CONTRACT:** Bagger denies application roles its private dispatcher, key getter and owner controls; requires HMAC plus durable single-use reservations; and refuses unsafe queue/Vault ACLs before committing dispatch. The original local model used owner-owned private provider substitutes. That was a valid protocol model, but did not prove portability of provider grant ownership/defaults.
- **LOCAL MODEL / INFERENCE:** Real PostgreSQL 17, separate provider/managed owners and provider-shaped grants reproduce the inability to revoke someone else's grants. Grant option permits grants/revocation through one's own grant chain, not removal of an independent provider-origin grant. Hiding a schema from the API is separate from denying that SQL role access. [PostgreSQL REVOKE contract](https://www.postgresql.org/docs/17/sql-revoke.html), [focused model](evidence/LOCAL-MODEL.json).

Default privileges affect future objects created by the selected role; they neither remove existing extension grants nor override explicit grants inside provider extension installation scripts. They are not a portability fix. New Bagger objects must still revoke PUBLIC execution/access explicitly in the same transaction. [PostgreSQL default privileges](https://www.postgresql.org/docs/17/sql-alterdefaultprivileges.html).

The changelog review confirms that the old database JWT-secret setting is unavailable and direct cron table edits are unsupported. This supervisor already uses a distinct signing key and `cron.schedule`, not either bypass. Supabase documents SQL scheduling as a supported mechanism; actual cron database user/permissions, net helper invoker/definer modes and extension ABI remain next-install catalog gates, not assumptions from a local substitute. [Changelog review](evidence/CHANGELOG-REVIEW.json), [scheduled HTTP pattern](https://supabase.com/docs/guides/functions/schedule-functions).

## Effective threat model

`PUBLIC` is a privilege pseudo-role, not a login credential. Hosted `anon`, `authenticated` and `service_role` are NOLOGIN; possession of a publishable/server key or Auth JWT does not itself provide a database connection or arbitrary SQL. The following distinctions are essential.

| Path | Current evidence and consequence |
|---|---|
| PUBLIC/anon/authenticated/service_role → pg_net SQL | The retained extension probe shows PUBLIC object privileges. Upstream grants schema USAGE too; the local model proves that combination permits arbitrary SQL HTTP URL/body/headers and queue reads/writes. pg_net is currently **not installed**, so no actual HTTP invocation was attempted here. Future installed schema USAGE/ABI must be measured. |
| API caller → net/vault/private Bagger schema | Six GET-only `limit=0` probes, using anon and server-key authority, returned 406/PGRST106 for all three schemas. No rows returned. This proves current direct Data API profiles are unavailable; it does not certify future exposure or SQL-role denial. |
| API caller → generic SQL/HTTP proxy | Source inspection found no application pg_net/Vault access outside the private supervisor SQL. Hosted public function inspection found no direct net/vault/cron proxy. The reachable dynamic wrappers inspected use fixed targets or a private allowlist with canonical guards, not caller-supplied SQL/URLs. pg_graphql is not installed; its public placeholder reports unavailable. This is bounded source/catalog evidence, not a general SQL-injection audit. |
| anon/authenticated SQL → Vault | No Vault USAGE or SELECT. Denied. |
| service_role SQL → Vault | USAGE and decrypted SELECT are present; create/update/decrypt helpers are also granted. A future signing key stored in this view would be readable without the Bagger key getter. Vault is currently empty, so no key was exposed or retrieved. |
| client → Bagger dispatch/key/control | EXECUTE denied for anon/authenticated/service_role on all 15 private supervisor functions. No participant or Director entitlement expands these privileges. A fixed SECURITY DEFINER wrapper with revoked EXECUTE can contain its own authority, but cannot remove direct provider grants. |
| generic HTTP → worker | Missing/wrong HMAC is denied before BEGIN. Even a correct HMAC cannot invent a reservation. Body fields, exact immutable origin/path, resource/release binding, 30-second expiry and single-use CAS remain required. |
| queue reader → an already-issued signed ticket | The signature is not the long-lived HMAC key, but an issued ticket is a short-lived bearer permit. A reader can preplay it before its first use; CAS denies the second use, not first-use capture. An optional Vercel bypass header would be a separate, longer-lived credential. A private wrapper does not make provider queue headers private. |

The Management API configuration read returned 403. Its reason was not established (expiry and insufficient scope are both possible). The six Data API profile denials remain direct independent evidence; full exposed-schema/search-path configuration readback is **pending**, not fabricated. [API exposure probes](evidence/HOSTED-API-EXPOSURE.json), [Supabase schema exposure contract](https://supabase.com/docs/guides/api/using-custom-schemas).

## Preferred approaches, evaluated in order

| Approach | Outcome under the requested boundary |
|---|---|
| A. Bagger-owned private fixed SECURITY DEFINER wrapper | Can deny clients the Bagger dispatcher and arbitrary target selection. It cannot by itself prevent `service_role` decrypted-Vault SELECT or PUBLIC queue access. Do not replace the current ACL guard with an API-hiding-only assertion. |
| B. pg_cron → private dispatcher → pg_net | Supported scheduling arrangement. Run as the narrow reviewed managed owner; no client cron grant. Has the same secret and queue limitations as A. Changing invoker to definer alone does not resolve them. |
| C. documented Vault integration | Supported for encrypted storage and SQL retrieval. The observed provider defaults do not meet this repository's stronger requirement that direct `service_role` secret access be denied. A restrictive Bagger view does not remove SELECT on the provider view. |
| D. documented provider revoke operation | No supported operation granting managed `postgres` authority over these provider-origin ACLs was established. Dashboard SQL runs as `postgres`; changing ownership, impersonating `supabase_admin`, extension internals or relying on REVOKE warnings is not a remedy. Provider support could identify a supported mechanism; none is presumed. |
| E. Edge Function / other transport | Reconsider only after reviewing the missing secret and transport boundaries. An Edge Function reached through the same readable queue with a static bearer header merely moves the leak. Its root signing material could be kept in provider runtime secrets, but scheduler authentication, first-use capture and exact deployment reservation still need a reviewed design. No new function, scheduler, paid resource or external service was created. |

## Minimum design decisions still required

1. **Secret custody:** retain provider Vault only if Supabase supplies a documented supported way to remove direct `service_role` access. Otherwise review a Bagger-owned private secret store or a runtime secret holder outside Vault. An owner-owned SQL secret table can enforce SQL grants, but plaintext logical dumps do not preserve Vault's separate-key authenticated encryption. It is not an equivalent replacement and was not implemented silently. Copying Vault ciphertext/private crypto helpers into another table would depend on undocumented provider internals and is rejected.
2. **Transport custody:** the scheduler must not place a reusable protection credential in a PUBLIC-readable queue. If the accepted boundary also denies SQL-role first-use access to an issued worker permit, pg_net AS-IS cannot carry that permit in readable plaintext. Review a transport that preserves that boundary, or explicitly review the narrower API-only/owner-issued bounded-permit threat model. The review does not approve relaxing it.

The desirable fixed path remains pg_cron → private dispatcher → exact immutable Vercel deployment → existing bounded Node worker, only if these two decisions are resolved. No generic proxy is proposed. Signing remains HMAC over POST/path/origin/body hash, with 30-second expiry and single-use database reservation. Origin comes from the exact current Certification binding; path is `/api/internal/derived-worker/run`; method/body/header schema are fixed. No arbitrary resource, URL, method, client headers or Production fallback is accepted by the Bagger path. Provider pg_net's own arbitrary SQL capabilities are explicitly not claimed to be removed.

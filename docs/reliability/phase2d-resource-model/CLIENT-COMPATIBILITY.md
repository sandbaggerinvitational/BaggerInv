# Client and transport compatibility design

Status: **PROPOSED — NOT IMPLEMENTED / NOT RECERTIFIED.** Base `7cec5128409286f5b4a5f3524d4c5488124a7be7`. Historical P0 A–F proof is preserved. This document describes candidate changes for owner approval, not a new P0-F PASS.

## Contract rule

Resource selection is a server deployment decision backed by the [registered resource trust chain](SECURITY.md). A browser, native client, query string or request JSON must not choose the database/resource. Existing Production routes retain their current admission, request/response/error contracts and scoring meaning. Certification uses the same domain logic behind separate resource admission. No Google transport or fallback is introduced.

No PWA or Build 10 score DTO change is proposed. No native shipping source change is proposed. The native-development fixed Preview pin is a separate existing boundary; backend-model compatibility does not establish that a shipping device can be pointed at a new hosted resource. Any such claim remains NOT PROVEN and outside this design.

## API effects requiring explicit design approval

1. **New certification annual route:** `GET/POST /api/director/canonical-future-tournaments`. It is unavailable without installed certification resource/schema/context, requires existing authorized synthetic Director or owner entitlement as the particular annual action requires, and requires same-origin mutation transport. It shares the generic year/target semantics already corrected by annual CREATE. Current/governance/resource identity is always server-bound. A target year/tournament ID remains validated domain input inside the same resource; it is not a resource selector. CREATE retry, revision conflict and canonical readback semantics remain identical to the existing annual contract.
2. **Certification internal RPC envelopes:** Add exact resource/installation/schema/release context only at server-to-database boundaries, with a distinct version where signatures change. Public client DTOs do not gain raw `resource`, project URL, service key, actor or governance fields. Production wrappers continue validating the original Production envelope before calling shared cores.
3. **Certification Director context token:** Include resource identity/revision and installation identity in the new gateway version's server-generated canonical fingerprint. Do not modify the existing v1 isolated RPC fingerprint or its legacy binding table. The HTTP adapter preserves the supported shape while token consumers treat it as opaque. Old context from another resource or revision conflicts; it does not silently refresh/rebind. Same-operation recovery keeps the original operation ID and returns COMMITTED/UNKNOWN according to its exact durable receipt. No new mandatory client field is added to PWA/Build 10 score/recovery DTOs; certification resource binding is carried by server admission and its internal receipt context.
4. **Error meanings:** Missing resource/schema/transport is unavailable (503); absent actor authority is denied (403, preserving existing signed-out route behavior); malformed or privileged input is invalid (400); stale resource/domain context is conflict (409). Preserve established domain meanings. Proposed certification-specific failures use an explicit `CANONICAL_RESOURCE_*`/existing `DIRECTOR_OPERATIONS_*` mapping reviewed by the affected client parsers. No canonical failure triggers Google fallback or a global participant-session reset.
5. **Annual UI wording:** A certification-only rendering must not label synthetic work “Production Owner annual administration.” Minimal wording/route parameterization is required if that existing panel is reused. This is truthfulness of context, not a broad interface redesign.

BREAKING CHANGE: **NO intended break to supported Production/PWA/Build 10 contracts.** Certification internal RPCs and its new additive annual API are new versioned contracts. This is a design intention, not demonstrated compatibility. The unchanged legacy Preview path must retain or explicitly fail closed under its own resource profile; it is not silently upgraded into registered CERTIFICATION authority.

## Deployment and rollback implications

Old Production app/new schema compatibility is conditional on retaining unchanged Production wrappers, defaults and original response/error fields while their internal cores gain explicit resource context. New app/old schema must fail closed for certification, without fallback or auto-migration. Production application rollback cannot depend on a certification registry entry or new credential. Certification app rollback to the base does not support the new dedicated resource and must become unavailable; it must not switch to the old shared Preview or Production. The detailed SQL sequencing belongs to [PRODUCTION-UPGRADE-DESIGN.md](PRODUCTION-UPGRADE-DESIGN.md).

No hosted configuration, resource creation, real identity, provider message, Google access, Production query, staging deployment, migration or source change is authorized by this design artifact. Owner implementation approval is still required.

A failed actor check must roll back context and create no admission row; runtime proof remains required.

# Proposed implementation scope and gates

> **Approved implementation addendum — 2026-09-30:** the resource model, truthful Certification-origin annual closure, and durable Certification ingress lifecycle are now owner-approved. **Implementation recommended: YES, subject to explicit owner approval of this design.** Nothing in this file is implemented. Source base: `7cec5128409286f5b4a5f3524d4c5488124a7be7`. This is a bounded canonical resource/control change, not a general environment abstraction. Historical P0 A–F PASS remains evidence for that base, not for the proposed implementation.

## Decisions to approve together

1. One immutable registered resource per physical database; only PRODUCTION and CERTIFICATION. Keep domain keys and one canonical implementation. No client resource selector.
2. Retain Production identity/admission and old isolated-v1 contracts. Add separately admitted certification gateways and private resource-context resolution, including scoring/recovery, annual, worker and read transports.
3. Move the existing current-pointer FK to the singleton resource registry. Add certification governance/release/admission state; no fake Production resource, cutover or Google provenance.
4. Separate a reviewed final-schema baseline from resource registration and synthetic bootstrap. Keep historical migrations immutable; the forward upgrade and fresh install must converge to the same selected catalog/profile.
5. Use a checked-in exact certification registration, initially disabled. After separately authorized future resource creation, actual identity review requires a registration commit, affected retesting and a **new final application SHA**. No deployable hosted candidate is frozen before its resource registration exists. Release authority pins that resulting SHA separately.

Approval to implement does not authorize creating that resource, registering a real hosted key, configuring Vercel, sending messages, deploying, or reading Production/old Preview.

## Deterministic fresh installer and synthetic bootstrap

Proposed new directory `supabase/canonical_bootstrap/` contains a reviewed final-schema SQL baseline, versioned object/source manifest and separate owner-only resource registration/bootstrap contracts. A proposed `tools/reliability/verify-canonical-install.mjs` orchestrates **local owned database** installation/comparison only; it cannot discover hosted credentials or run against arbitrary URLs. A synthetic fixture module under `test/support/reliability/` provisions test authority after schema installation using supported contracts.

The exact adjacent artifact profile is explicit in [MIGRATION-CLASSIFICATION.md](MIGRATION-CLASSIFICATION.md). Do not glob-install incremental candidates or promote an unreviewed optional profile into Production. Required shipping reads must have their actual installed RPCs; optional provider-backed workflows remain closed until their separate profile is certified. Fresh/upgrade catalog comparison uses the same explicitly selected profile, and unknown installed optional bodies stop an eventual upgrade preflight.

The installer must separate application schemas from managed Supabase Auth/platform objects. Local platform emulation is labeled; hosted Auth/owner/extension proof remains later. No `session_replication_role` bypass, Production resource seed, fabricated workbook, old Preview bootstrap or test mock may supply runtime authority. Installation never enables external cron/providers.

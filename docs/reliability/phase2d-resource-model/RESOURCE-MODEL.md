# Canonical resource/control model — proposed

Design base: `7cec5128409286f5b4a5f3524d4c5488124a7be7`. Status: **PROPOSED; implementation requires owner approval.** SOURCE findings are proven by the linked inventory; proposed enforcement is not implemented or certified. This document is the authority for proposed object names where companion documents describe them conceptually.

## Decision: one resource per physical database

Use only `PRODUCTION` and `CERTIFICATION`. Each physical database may contain **one immutable registered resource**, many tournament years, and one current tournament pointer. Production and certification never coexist in a database. They have separate Auth, credentials, storage and worker connections. This is not generic multi-tenancy. No resource selector is accepted from a client. Local proof uses two separate disposable databases and explicit test transport; LOCAL/TEST/PREVIEW are not additional canonical classes.

Keep the canonical golf, identity and private control schema namespaces. A historical namespace or function name containing `production` may remain for compatibility; an active Production identity, activation or provenance may not be fabricated in certification. Both install paths converge to the same canonical definitions, with different explicitly registered control data.

Hosted execution class is constrained by the reviewed registration: existing Production uses its existing Production deployment contract; CERTIFICATION uses the exact approved Preview deployment. These are transport/admission predicates, not additional canonical resource classes. Local proof uses explicit test-owned transport injection, never a shipping environment flag that admits arbitrary loopback or hosted resources.

## What is wrong now

Migration001 creates and seeds `production_control.resource_scope` with one fixed Production ref/origin/domain/workbook. Migration064 makes `current_tournament_pointer_v1.scope_key` an FK into that table and seeds Production current/future resource rows. Migration128's isolated Director assertion reads that Production-scoped pointer. Ordinary score admission, annual platform guards, derived intent flushing/delivery and delivery provenance also consume Production control rows. Separately, ordinary Preview transport uses older Preview scoring/read RPCs; accepting another URL does not install or select the canonical Phase2 RPC contract. See [dependency inventory](DEPENDENCY-INVENTORY.md).

## Proposed registration and control objects

| Object | Minimum fields/semantics | Why required |
|---|---|---|
| New `production_control.canonical_resource_v1` | Singleton key with one-row constraint; unique `resource_id`; `resource_class`; immutable installation UUID; exact project ref/HTTPS origin; expected Vercel team/project; reviewed registration-manifest digest; positive registration revision; schema/bootstrap contract. Optional provenance descriptor only where existing projection contracts need it. | Independent owner-installed database identity; no runtime role can create, rotate, or reclassify it. |
| Existing `production_control.resource_scope` | Existing Production row, identity, columns, checks and authority semantics retained on Production; table empty in a fresh certification install. | Compatibility anchor for existing Production admission. It is not the new certification registry. |
| Existing `production_control.current_tournament_pointer_v1` | Retain table, revisions and Production row/key. Replace its resource FK with an FK to the new registry. Production `scope_key` remains `BAGGER_INV_PRODUCTION`; certification `scope_key` equals its distinct registered resource ID. Permit the new canonical pointer contract only for certification while preserving the old Production contract value. | One actual pointer per database/resource, not parallel legacy/canonical pointers requiring synchronization. |
| New `production_control.certification_admission_v1` | Resource/class FK fixed to CERTIFICATION; binding UUID; closed/open state; exact approved branch, commit, deployment identity/origin; activation epoch/revision and admission revision; governance tournament FK; schema digest/contract. Expected team/project are inherited from the registry rather than competing copies. | Synthetic release and activation authority, independent of Production cutover/maintenance/release tables. |
| Existing `production_control.isolated_director_context_v1` | Preserve its exact legacy/local v1 compatibility behavior. Do not widen its old ref check. New certification gateways use the new resource/admission context instead. | Avoid turning an old compatibility binding into arbitrary resource authority. |
| New private `production_control.canonical_operation_context_v1` | Transaction-local owner-only marker keyed by backend PID + transaction ID; resource/admission/operation identity and bounded provenance. The Production `resource_id` reuses `BAGGER_INV_PRODUCTION`: no new public Production identity is invented. A certification resource uses a unique owner-registered `CERTIFICATION:<uuid>` value and a unique installation ID. Neither ID grants actor authority. Resource class/ref/origin/installation identity is immutable. An ordinary credential rotation keeps that identity: close admission, review the new credential provenance and manifest revision, update through owner-only registration control, and recertify before reopening. Resource relocation or reclassification requires a new explicitly reviewed registration/database, not editing a URL in place. Deployment/admission revisions remain separate from registration revision. The original bootstrap contract records installation provenance; the installed schema capability/version is verified independently on each supported upgrade.

Do not add a resource ID to every score, golfer, match, receipt or job. Physical singleton isolation makes existing tournament/match/job keys sufficient. Resource-bound control records and external recovery/deployment contexts need identity; the domain rules do not need tenant columns. Any future request to co-locate resources invalidates this design and requires a separate architecture review.

## Current and governance tournaments

The current pointer selects the resource's operational tournament. Governance selects the tournament whose existing owner/Director entitlement authorizes annual transition; it is not inferred from a client target or automatically changed when current advances. Production continues using its existing 2026 governance and existing annual pointer rules. Certification explicitly registers its own synthetic governance tournament and current pointer.

Initial certification may use synthetic tournament ID/year `2026` to exercise existing fixed-2026 contracts. That does not import any real tournament data or Production resource authority. Do not generalize the existing setup/financial cores' 2026 scope merely to add certification. Annual CREATE retains separate current-authorization year and validated future target year; CREATE does not mark a tournament Ready or advance current. Annual transition must apply the same readiness, current-pointer CAS, admission fence, drain and lease conditions against certification-local control records.

## Shared canonical execution

The design is `admitted wrapper → private canonical core → durable result/receipt/audit`. Existing Production wrappers keep their resource, actor, release, revision, ingress and lifecycle checks and externally visible behavior. New certification wrappers validate CERTIFICATION registration, deployment/admission, current/governance, actor and revisions, then call the same domain core. Existing P0F setup and reduced financial cores are reused; scoring/finalization/recovery, annual administration and worker dispatch need equivalent reviewed separation where Production admission is embedded today.

Introduce private context resolvers for current pointer, governance, release/admission, resource provenance and worker scope. Resolve from the singleton database registration plus an admitted caller, never from an arbitrary `resource_id` argument. At transaction start and after relevant locks, verify expected revision/token and resource again. Preserve original lock order and do not cache a write authorization across revocation. Production compatibility helpers must return exactly the original Production context; they must not select certification because a row or environment flag happens to exist.

The private transaction marker is established by the outer admitted wrapper. Nested calls must retain the same resource/installation/admission context, cannot replace it or clear their parent's marker, and retain outer operation identity alongside existing child receipt identities where needed. Normal completion clears only the marker owned by that wrapper; failure rolls back with the canonical mutation. This nesting behavior is a mandatory runtime test, not permission to bypass a nested wrapper's actor/domain checks.

The new certification score gateway must select the canonical Phase2 submit/finalize/recovery path. It must not reuse old Preview `submit_hole_score_authoritative` as a substitute for the certified canonical core, or pass fabricated Production fields to the Production wrapper. Likewise the targetless worker runner receives an explicitly admitted certification adapter while reusing its queue processing/retry algorithms.

## Constraints, receipts and provenance

- Keep domain primary/unique keys, score payload hashes, financial revisions and Production replay semantics unchanged. Admission precedes receipt lookup, job claim and private reads. Certification recovery handles/context tokens include installation/resource revision; Production formats remain unchanged.
- Replace fixed active History/Draft/Guide project checks only where a certification capability actually uses them. Existing `project_ref` or `(project_ref, project_url)` columns can reference the singleton registry's unique exact values. Do not mechanically add resource columns or weaken checks to arbitrary domains. Retired Google worker configuration remains empty on certification, not enabled under a renamed resource.
- Preserve existing Production workbook/provenance values and historical audit. Certification uses an explicit non-Google synthetic provenance identifier (for example a URN derived from its installation ID), supplied by the database context. Historical column names may remain; the value must never be a fabricated Production workbook or a delivery destination. Class-specific registration/constraint validation preserves the Production case and admits only the registered synthetic descriptor.
- Use existing JSON audit details for certification resource/operation identity. Delivery attempts currently have a trigger reading Production activation; certification handling provenance must come from the admitted transaction context. Record its immutable resource/installation/registration/admission/release/operation snapshot in existing `operation_audit_events.details`, linked by `delivery_event_id`, in the same transaction. Migration129 already uses this event linkage for narrow isolated financial provenance. Preserve that legacy path; use a distinct certification event meaning. No new audit sidecar or broad domain audit columns are proposed. A certification delivery event without valid admitted context must fail, not acquire Production defaults. If implementation reveals a required audit family cannot be linked accurately this way, stop for design review instead of widening schema opportunistically.
- Direct private context/core execution remains denied to PUBLIC, anon, authenticated and runtime service_role. Public RPC grants are service-only and each wrapper performs complete admission. RLS/account/financial privacy checks remain independently required.

## Trust and candidate sequencing

Use the checked-in exact registration manifest described in [SECURITY.md](SECURITY.md), initially disabled. Runtime environment values cannot manufacture registration. After a later owner-authorized resource creation, review the actual ref/origin/installation/key provenance, commit the exact non-secret registration, rerun affected proof, and only then freeze the final application SHA. Store its exact release binding separately to avoid a self-referential Git hash. This is a deliberate change to the earlier assumption that a deployable final SHA could be fixed before the resource exists; owner approval must include this sequence.

No signature/PKI service, resource autodiscovery, generic project allowlist, client resource query parameter, Google fallback or Production shadow/cutover workaround is proposed. Environment checks do not prove execution location against an administrator who possesses the keys; future hosted management readback and credential proof remain mandatory.

## Design invariants and limits

No registration: no canonical runtime authority. Two registrations: installation/activation fails. Class/ref/origin mismatch: deny. Stale revision: conflict. Wrong schema: unavailable, no auto-migration. Wrong actor or target: existing denial. Certification wrapper on Production or Production wrapper on certification: deny before lookup/write. Workers recheck current scope for each claim and completion. No synthetic publication happens automatically.

These are required implementation tests, not observed results. Production semantics are intended to be unchanged; equivalence is a release-blocking proof obligation. No hosted identity, actual key provenance, database upgrade, clean install or new P0 PASS is claimed by this design.

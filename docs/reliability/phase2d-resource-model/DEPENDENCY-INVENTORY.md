# Canonical resource dependency inventory

Status: architecture review only. Base application: `7cec5128409286f5b4a5f3524d4c5488124a7be7`. Evidence layer: SOURCE. No SQL installation, hosted query, source modification, or new runtime proof was performed for this inventory. Existing Phase 2 P0 results remain historical evidence and are not reclassified here.

## Finding and proposed boundary

**PROVEN — the resource dependency is semantic, not a naming problem.** The canonical domain tables mostly scope authority by tournament and match. The surrounding admission, pointer, release/activation, worker and audit functions repeatedly select the singleton `BAGGER_INV_PRODUCTION`. A fresh certification database cannot satisfy those paths accurately by adding one new Supabase ref or by inserting a fake Production resource row.

**STRONGLY SUPPORTED — one admitted canonical resource per physical database is the minimum coherent boundary.** Keep the existing Production resource and behavior in its database. A dedicated certification database has one separately installed `CERTIFICATION` resource and its own pointer, governance, release/admission revisions and epoch. Reuse the canonical domain tables and calculations; no co-located multi-resource tenancy, resource argument supplied by participants, new participant role, resource column on every golf table, or copied scoring implementation is justified by this task.

**PROPOSED — implementation strategy now resolved.** The companion [migration classification](MIGRATION-CLASSIFICATION.md) inventories all120 canonical migration files and15 supplemental artifacts. The design selects Strategy B: one reviewed final canonical baseline for fresh install and a separate forward upgrade that converges to the same canonical catalog. This resolves the architecture choice; final installed body hashes, owner/ACL/OID dependencies and bootstrap behavior remain future implementation proof gates, not an unresolved reason to select a different model. No migration has been authored or executed here.

In the following tables, `PC` means `production_control`, `SA` means `scoring_authority`, and `PI` means `participant_identity`. These are existing schema names, not a recommendation to rename them. “Change” means change needed for an actual certification path, not automatic replacement of the existing Production entry point.

### Synthetic provenance is distinct from resource authority

**PROVEN:** base migration002 also fixes `source_workbook_id` to the historical Google workbook on `completed_history_current_revisions` (1471), `completed_history_revisions` (1503), `draft_revisions` (1557), `guide_content_revisions` (1594), `guide_projection_current` (1601), `guide_sync_runs` (1617), and `guide_sync_worker_configuration` (1627). These constraints are separate from the project-ref constraints. A certification fixture must not lie about having been imported from that real workbook.

The proposed certification registration may carry a non-authoritative synthetic provenance descriptor such as `urn:bagger:certification:<installation-uuid>:fixture:<version>`. Active project-bearing projections should bind their exact project ref (and URL where stored) to the singleton registry; this does not require resource IDs on all fact rows. New certification fixture provenance uses that descriptor. Existing Production values/meanings and immutable historical provenance stay unchanged. Retired Google worker configuration remains disabled/unpopulated; preserving historical schema is not permission to install a worker. Cache identity and SQL read envelopes must agree with the installed provenance and resource identity. Fixed2026 contracts remain fixed2026; resource isolation does not alter annual CREATE target-year semantics.

## Minimum implementation seams and proof obligations

1. **Single physical-resource registration.** Install exactly one immutable admitted resource class (`PRODUCTION` or `CERTIFICATION`) per physical database. Preserve existing Production record/behavior. The proposed registry is `canonical_resource_v1`: existing `BAGGER_INV_PRODUCTION` resource ID retained on Production; `CERTIFICATION:<uuid>` on the dedicated database, with exact ref/origin, installation UUID, manifest digest, revision and schema contract. Registration and revision change require owner-only/bootstrap authority; no runtime role may choose another ref or rewrite the binding. Fail on both/missing/ambiguous registrations.
2. **Resource-owned current control head.** Move `current_tournament_pointer_v1.scope_key` foreign-key ownership to `canonical_resource_v1.resource_id`, preserving the Production row value exactly. Production-specific `resource_scope`/cutover rows remain on Production and are empty on certification. A dedicated `certification_admission_v1` holds the certification release/deployment/governance/admission fields; it is not a Production mirror. Current tournament, governance tournament, release/admission revision, epoch, schema contract and enabled capabilities derive from that database's resource, never from client JSON or an `environment=PRODUCTION` fiction. Domain match/receipt/side-game keys need no resource column when there is only one resource per DB. Cross-database clones must remain CLOSED until explicitly registered and proven.
3. **Admitted wrapper -> single private domain body.** Production wrappers retain exact original authority conditions. Certification wrappers validate its independent registered context before reusing the same canonical score/finalize/recovery, side-game and setup bodies. Existing130/129 cores provide a proven pattern for limited setup/financial operations; they do not cover all score/worker/publication paths. No participant/browser/service_role direct execute on private cores.
4. **Truthful audit.** Score receipts retain immutable Auth origin and match/mutation identity. Financial and delivery events must identify the actual certification control revision/release. Existing129 transaction-local auction override is intentionally narrow and cannot be treated as global delivery provenance coverage. A resource-control lookup can avoid adding fields across all domain tables, but runtime proof must show every audit record resolves unambiguously to its actual source.
5. **One canonical final catalog, two installation paths.** Follow [Strategy B](FRESH-INSTALL-DESIGN.md): generate, review and commit the final canonical baseline from the classified sources; separately forward-upgrade the supported prior catalog to that same schema/core definition set. Include current public/private RPC inventory, never borrow incompatible old Preview scoring or retired Google workers merely to make imports resolve. Fresh install creates definitions and reviewed static contracts before registration/synthetic authority, and stays CLOSED/inert until bootstrap. Runtime source hashes, owners/ACLs/trigger ordering and normalized stored dependencies must converge; historical source patches are not replayed against already-final bodies.
6. **Proof before reuse.** Re-run runtime function owner/ACL/`search_path`/security-mode/dependency and nested-caller proof. New certification wrappers need their own admitted context; do not mutate the legacy isolated-v1 contract into a broader selector. - **PROVEN:** no certified resource-neutral score/recovery/worker transport spans the ordinary Preview and canonical migration profiles today.
- **PROVEN:** canonical worker admission, current pointer and delivery audit provenance depend on a Production-scoped control row beyond the isolated Director binding.
- **PROVEN:** completed History project-ref constraints and ordinary Preview read envelopes are resource-bound; a new schema cannot simply replay one lineage then point all adapters at it.

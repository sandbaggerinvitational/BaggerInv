## Preserved original design review

The section below is historical, retained verbatim. Its request to approve implementation and statements that implementation/proof had not begun describe the earlier design gate, not the current decision.


**Design recommendation: approve bounded implementation. No implementation or hosted action has occurred.**

The current database schema can contain canonical scores without Google, but its control paths still assume the one Production resource. The annual current pointer references that resource; scoring admission, isolated Director context, workers and delivery audit also read Production control rows. Ordinary Preview scoring uses a different legacy RPC path. Changing a URL cannot safely make a new database run the certified canonical path.

The minimum proposed model is **one registered resource per physical database**, class **PRODUCTION** or **CERTIFICATION**. Production keeps its identity, pointer, release/admission rules and data. A separate certification database gets its own exact owner-reviewed registration, synthetic governance/current tournament and release/admission state. Clients cannot select the resource. Both use the same golf/domain tables and private logic through separately admitted wrappers.

The design adds a private resource registry, certification admission row and narrowly used transactional audit-context marker. It changes the existing current-pointer foreign key and required project/provenance constraints. It does **not** add tenant IDs to all scores, results, players, receipts or jobs. Production backfill is descriptor metadata, not a competitive-data migration. No rule, entitlement, financial/privacy policy or Google restoration is proposed.

A fresh database needs a reviewed final-schema baseline, followed by explicit registration and synthetic bootstrap. Replaying the120 historical files unchanged would create Production-shaped control state; that is rejected. Existing Production instead takes new forward migrations. Both paths must converge to the same selected schema and canonical implementation. Historical migrations/evidence remain unchanged.

The largest risks are embedded Production checks beneath wrappers, stored/dynamic SQL dependencies, incomplete install profiles, privilege defaults and false audit provenance. The implementation must demonstrate actual SQL/HTTP behavior, Production equivalence, two-database isolation, all six affected P0s,432 zero-Google holes/24 Finals, bounded history performance, test accounting and rollback. None of that new proof exists yet. Historical P0 A–F PASS at `7cec5128409286f5b4a5f3524d4c5488124a7be7` remains intact.

Old application/new schema compatibility is **conditional**, with preservation as a release gate. The base app cannot serve a newly registered certification resource; rolling that resource back closes admission, rather than switching it to Preview or Production. No safe destructive database downgrade is promised before tests.

One sequencing decision needs explicit acceptance: implement with hosted registration disabled; later create and verify a dedicated resource under separate authorization; review and commit its exact non-secret registration; rerun affected proof; then freeze the final deployment SHA and bind it in release authority. The final hosted SHA cannot precede the actual resource registration.

**Decision requested:** approve implementation of the scope in [IMPLEMENTATION-PLAN.md](IMPLEMENTATION-PLAN.md), or return revisions to this design. Approval would not authorize resource creation, Vercel changes, hosted migration/deployment, Production access, Google access or Build11. This package stops at the design gate.

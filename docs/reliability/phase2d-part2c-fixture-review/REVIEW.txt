DECISION

The installed schema supports multiple annual tournament identities. It does
not support a second canonical 2026 identity: tournaments.tournament_year is
unique, and future_tournament_catalog_v1 requires tournament_id = year::text.
The current pointer is one row per resource scope. Future annual administration
requires a later numeric year and a guarded PREPARE/CLOSE/DRAIN/ACTIVATE chain.
Activation requires a closed/certified predecessor. The current secondary is
not FINAL/complete. No pointer overwrite, forged certificate or early closure
is proposed.

Even a lawful future-year transition would not satisfy this rehearsal's current
execution contracts: worker_supervisor_binding_v1 requires current tournament
2026 and the exact existing Certification resource/project; its work accounting
also selects 2026. The admitted Net Skins configuration adapter requires 2026.
Future-year domain support is real; it is not interchangeable with the hosted
Part 2B delivery/configuration paths. Making Model B work would require another
reviewed execution/configuration scope extension, rather than a structure-only
owner provisioner. No such change was made.

Model A could add structure without claiming a fresh tournament identity. It
could certify full-state completion, but cannot certify a beginning-to-end
chronology: existing hosted Round 3 Final/result/side-game/Odds events would
predate the added R1/R2 execution. They must not be backdated or relabeled.

Model D preserves the existing resource completely and starts canonical 2026
from zero in a physically isolated database. This is the preferred architecture
for a truthful pre-tournament -> R1 -> R2 -> R3 -> Final Results -> FinalRecap
rehearsal. It was assessed, not created or provisioned.
